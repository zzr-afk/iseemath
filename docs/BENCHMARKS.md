# 性能基准记录

## 环境

| 项 | 值 |
|---|---|
| 机器 | Intel Core i7-14650HX / 31.7 GB RAM |
| 系统 | Windows 11 家庭中文版 (26200) |
| 浏览器 | Chrome（headless，CDP 驱动） |
| 构建 | `pnpm dev`（Vite 6 开发服务器），未压缩 |
| 测量方式 | 页面内 `performance.now()` + 50ms 间隔存活计数（`ticks` 反映主线程是否被阻塞） |

夹具由 `E:/temp/claude/gen-bench.mjs` 生成，列结构为 `server,level,damage,ts`（2 个字符串列、2 个数值/文本列）。测试时把夹具临时放回 `public/`，测完移出，避免进入构建产物。

## 结果

### 18.1MB / 550,000 行

| 操作 | 耗时 | 主线程 |
|---|---|---|
| 导入预览解析（Worker） | 1.94s | 存活 33 次 / 预期 ~38 次，基本不冻结 |
| 保存到项目（写 18MB Blob + 文档提交） | 1.38s | 存活 13 次 |
| 刷新后重建（改造前，主线程解析） | 1.58s | 存活 2 次，明显冻结 |
| 刷新后重建（改造后，Worker 解析） | 2.40s | 存活 37 次，可交互 |

### 50.0MB / 1,620,000 行

| 操作 | 耗时 | 主线程 |
|---|---|---|
| 导入预览解析（Worker） | 5.77s | 存活 96 次 / 预期 ~115 次 |
| 保存到项目（写 50MB Blob + 文档提交） | 1.58s | 存活 13 次 |
| 刷新后重建（Worker） | 6s 量级 | 可交互 |
| 聚合：按 `server` 分组 + count + sum（8 组） | 0.42s（纯计算） | — |
| 聚合：按 `level` 分组 + count + sum（80 组，UI 端到端） | 0.65s | 存活 1 次 |
| 聚合：按 `level` 分组 + count + p90（80 组，纯计算） | 0.90s | — |

### 聚合优化前后（1,620,000 行，纯计算）

| 查询 | 优化前 | 优化后 |
|---|---|---|
| `level` 分组 + count + sum（80 组） | 0.71s | 0.21s |
| 含 `p90` 的同一查询 | 1.30s | 0.90s |
| `server` 分组 + count + sum（8 组） | — | 0.42s |
| 同一查询的 UI 端到端（Server → level 切换） | 1.58s | 0.65s |

优化内容：

1. 不再为每个分组保存全部行号数组，改为单遍增量累加（count/sum/avg/min/max），仅分位数指标保留值数组。
2. 单列分组键直接作为 `Map` 键（数字/字符串零分配），多列分组才拼稳定键；不再逐行 `JSON.stringify`。
3. IANA 时区分桶复用缓存 `Intl.DateTimeFormat`，并按原始时间戳 memo 分桶结果。

## 结论

- M2 验收目标「50MB CSV 导入 <15s、聚合正确、UI 不冻结」中的导入与重建已达成；聚合在 160 万行、双指标下端到端约 0.65s，属于可感知但短暂的停顿，分位数指标约 0.9s。
- 18MB 文件的刷新重建从「1.6s 冻结」改为「2.4s 可交互」，代价是解析结果需一次结构化克隆。
- 100MB 目标按 18MB/2s、50MB/5.8s 线性外推约 11–12s（数值为主），M4 再用真实 100MB 夹具复核内存峰值。
